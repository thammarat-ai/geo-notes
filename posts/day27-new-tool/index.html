โจทย์ทางการวันนี้คือ “The challenge has always been about learning things. Try out a new tool in your mapmaking workflow.” (หัวข้อ New tool — ดึงข้อความมาจากหน้า 30daymapchallenge.com อ่านสดวันที่ 27 พ.ย. เก็บสำเนาไว้ที่ scratch/chal27.html)

ผมใช้เครื่องมือใหม่มา 26 วันแล้ว (pyosmium, networkx, pyproj, shapely, h3, geopandas…) ดังนั้น “ใหม่” ของวันนี้ต้องเป็นของที่ผม ยังไม่เคยใช้จริงในซีรีส์นี้ ซึ่งผมเลือก DuckDB พร้อมส่วนเสริม spatial — เครื่องมือที่ทำงานกับข้อมูลแบบตารางและทำ ทุกอย่างเป็น SQL

คำถามที่ผมถามเครื่องมือใหม่ไม่ใช่ “มันเร็วกว่าไหม” แต่เป็น

ถ้าให้ SQL ตอบคำถามเดียวกับที่ Python เคยตอบ คำตอบจะตรงกันไหม และถ้าไม่ตรง ต่างกันเพราะ เครื่องมือ หรือเพราะ นิยาม/การเตรียมข้อมูล

๐. เครื่องมือและข้อมูล

DuckDB 1.5.5 + duckdb-spatial eb1e57c (ติดตั้งจาก repository อัตโนมัติ, มีฟังก์ชัน ST_* 158 ชื่อ ใน build นี้) บน windows_amd64

๑. กับดักที่ 1 — ตระกูล spheroid รับพิกัด (ละติจูด, ลองจิจูด) แล้วโกหกเงียบ ๆ

ST_Distance_Spheroid, ST_Area_Spheroid, ST_Length_Spheroid, ST_Distance_Sphere ใน DuckDB spatial ตีความตัวเลขตัวแรกเป็นละติจูด ซึ่งกลับด้านกับ ST_Point, ST_Contains, ST_Area (planar) และกลับด้านกับมาตรฐาน GeoJSON/WKT ที่ทั้งโลกใช้

ผลคือเมื่อป้อนตามมาตรฐาน มัน ไม่ error — มันคืน NaN

สิ่งที่ทดสอบ ป้อน (lon, lat) ตามมาตรฐาน ป้อน (lat, lon)
ระยะทางระหว่างจุด (4 เคส) NaN 4/4 ตรงกับ pyproj ต่างสูงสุด 0.000 ม.
พื้นที่ห่วงพื้นที่คุ้มครอง (40 ห่วง) NaN 40/40 ตรงกับ pyproj ต่างสูงสุด 0.0000 ตร.กม.
พื้นที่ประเทศไทย (1 polygon) NaN 514,453.7 ตร.กม. = ค่า pyproj เป๊ะ

ผมคิดว่านี่คือบทเรียนที่แพงที่สุดของการลองเครื่องมือใหม่: ความล้มเหลวที่เงียบที่สุด คือค่าที่ type ถูกต้อง NaN หนึ่งตัวในคอลัมน์พื้นที่ไม่ทำให้สคริปต์ล้ม มันแค่ทำให้ median() เป็น 0 แล้วคุณเขียนโพสต์ต่อโดยไม่รู้ตัว (และถ้าใครเคยอ่าน Day 22 จะจำได้ว่า ผมเคยพลาดเรื่อง “ป้อนพิกัดผิดระบบให้ pyproj” มาแล้วครั้งหนึ่ง — คราวนี้พลาดซ้ำในเครื่องมือใหม่ แต่จับได้เพราะตั้ง assert ไว้ว่า “ค่าที่ออกต้องไม่ใช่ NaN”)

๒. กับดักที่ 2 — ST_Transform ใน build นี้แปลงพิกัดไม่ได้เลย

ผมขอแปลงจุดหนึ่งไป EPSG ที่ต้องใช้ในงานนี้ 4 ตัว ผลคือ inf ทั้ง 4 ตัว (EPSG:3857, 32647, 32648, 6857) และมีเพียง 4326→4326 ที่ “สำเร็จ” เพราะไม่ต้องแปลงจริง ส่วน proj4 string แบบที่ซีรีส์นี้ใช้อยู่ (+proj=eqdc +lat_0=14 …) DuckDB ปฏิเสธตั้งแต่ parse: “The ‘target_crs’ parameter … is not a recognized coordinate reference”

ผลข้างเคียงต่องานนี้คือ SQL วัดระยะในระนาบ Equidistant Conic ของซีรีส์ไม่ได้ ผมจึงต้องวัดด้วยสูตร spheroid (ซึ่งกลับกลายเป็นข้อดี เพราะได้เทียบ “นิยาม” ไปในตัว — ดูข้อ ๕) และผมใส่ assert ที่บังคับให้โพสต์นี้ต้องอัปเดตไว้ด้วย: ถ้าวันไหน ST_Transform ใช้ได้ หรือถ้าวันไหนกับดักลำดับพิกัดหายไป สคริปต์จะล้มทันที ไม่ใช่เงียบไป

๓. งาน A — จังหวัดของ 83 จุด: SQL กับ geopandas ตรงกัน 83/83

SQL ฝั่งเดียวทำเสร็จใน 2 ประโยค (join ด้วย ST_Contains แล้ว any_value)

  • จังหวัดตรงกัน 83 จาก 83 จุด — นับทั้งจุดที่ ทั้งสองวิธีไม่พบ polygon ครอบคลุม ด้วย ซึ่งมี 3 จุด: เกาะพะลวยบีชบังกะโล (สุราษฎร์ธานี), โซเนวา คีรี รีสอร์ท (ตราด), หอดูดาวเฉลิมพระเกียรติฯ สงขลา — ทั้งสามเป็นเกาะ/ชายฝั่งที่ NE 10m ไม่มี polygon ครอบคลุม
  • เวลา: SQL 0.011 วิ · geopandas sjoin 0.012 วิ (พอ ๆ กันในงานขนาดนี้)
  • ทะเบียน (ชื่อไทย) กับ NE (ชื่ออังกฤษ) ตรงกัน 75 จุด ไม่ตรง 5 จุด และนี่คือส่วนที่น่าสนใจ เพราะผมต้องสร้าง ตารางเทียบชื่อ ขึ้นมาก่อน โดยไม่ hardcode — ใช้เสียงข้างมากของ 83 จุดเอง ผลคือได้ 32 จังหวัด และ 5 ชื่อที่กำกวม (Buri Ram, Lop Buri, Mae Hong Son, Prachin Buri, Tak)
  • ทั้ง 5 จุดที่ทะเบียนไม่ตรง NE ล้วนอยู่ในชื่อที่กำกวม ซึ่งไม่ใช่เรื่องบังเอิญ: จุดที่ “เห็นต่าง” ทำให้ชื่อ NE นั้นมีชื่อไทยมากกว่าหนึ่งโดยนิยาม
  • แต่ใน 5 จุดนั้นมี 2 จุดที่ผมคิดว่า NE ต่างหากที่ผิด (หรืออย่างน้อยต่างจริง): อุทยานแห่งชาติเขาใหญ่ —ทะเบียนว่า นครราชสีมา แต่ NE 10m วางเส้นแบ่งจังหวัดไว้จนจุดนี้ ตกใน Prachin Buri; และอุทยานแห่งชาติแม่ปิง — ทะเบียนว่า ลำพูน แต่ NE ว่า Tak เส้นขอบ NE 10m หยาบกว่าเขตราชการ (เคยเตือนไว้ใน Day 23 แล้ว)

๔. งาน B — จุดในเขตพื้นที่คุ้มครอง: 40 คู่ = 40 คู่ แต่ 24 จุด ≠ 25 จุด

SQL กับ shapely ใช้ห่วงชุดเดียวกัน (163 ห่วง) ให้ คู่ (จุด, ห่วง) ตรงกันทุกคู่ 40 = 40 ไม่มีข้างใดข้างหนึ่งได้มากกว่าเลย — แปลว่าตัว อัลกอริทึม containment ของทั้งสองเครื่องมือเห็นตรงกัน

แต่จำนวน จุด ที่ Day 21 รายงานไว้คือ 25 จุด ส่วนวันนี้ได้ 24 จุด สาเหตุไม่ใช่เครื่องมือ แต่คือ ห่วงที่ผมให้ SQL ใช้เป็นเวอร์ชันลดรายละเอียด — poly_draw.json ของ Day 21 เก็บเส้นขอบไว้สำหรับ วาด (มัธยฐาน 8 จุดต่อห่วง สูงสุด 261 รวม 5,531 จุด) ขณะที่การตรวจ containment ตอนนั้นใช้เรขาคณิตเต็ม พูดอีกอย่าง: การเตรียมข้อมูลเปลี่ยนคำตอบได้มากกว่าการเปลี่ยนเครื่องมือ และนี่คือเหตุผลที่ผมต้อง export ห่วงชุดนี้เป็นไฟล์แยก (data/day27_rings.json.gz) แล้วบอกไว้ชัด ๆ แทนที่จะให้คนอ่านคิดว่า SQL ทำผิด

๕. งาน C — ระยะไปน้ำ: เครื่องมือตรงกันเป๊ะ แต่นิยามต่างกัน 0.14%

  • SQL (ST_Distance_Spheroid ป้อนกลับด้าน) กับ pyproj (Geod.inv) ต่างสูงสุด 0.000 ม. จาก 69 จุดที่วัดได้ และ rho = 1.000000 — สอง implementation ของสูตรเดียวกันต้องตรงกัน ถ้าไม่ตรงคือมีบั๊ก ไม่ใช่ “ความต่างของเครื่องมือ”
  • ตรวจข้ามวัน: ระยะระนาบ EQ ที่คำนวณซ้ำวันนี้ต่างจาก dist_line_m ของ Day 26 สูงสุด 0.048 ม. — ยืนยันว่าตัวเลขเก่าสร้างซ้ำได้
  • แต่เมื่อเทียบ นิยาม: ระยะระนาบใน Equidistant Conic กับระยะ geodesic จริง ต่างกัน มัธยฐาน 0.643 ม. (0.1399%) สูงสุด 26.757 ม. — เล็กจนไม่มีผลกับข้อสรุปของ Day 26 แต่มันคือตัวเลขที่ผมควรเขียนกำกับไว้ตั้งแต่แรก ไม่ใช่เพิ่งมาวัดวันนี้
  • ข้อค้นพบเพิ่มจากการไม่จำกัดจาน: ระยะไปโหนดลำน้ำใกล้สุด มัธยฐาน 805.6 ม. และ มีเพียง 3 จุด ที่ไกลน้ำเกิน 5,000 ม. — อุ่นฟ้าอิงดาวแคมป์ปิ้ง (5,877 ม.), โรงแรม เดอะเปียโน รีสอร์ท เขาใหญ่ (6,479 ม.), บ้านไร่ยายชะพลู (8,038 ม.) ทั้งสามอยู่ในกลุ่ม 17 จุดที่ Day 26 ว่า “ไม่มีน้ำในจาน” → 14 จุดจาก 17 จุดมีน้ำอยู่ห่างออกไป 5–8 กม. ขอบจาน 5 กม. เป็นตัวกำหนดคำตอบ ไม่ใช่ภูมิประเทศ

๖. งาน D — พื้นที่: ทำซ้ำตัวเลขของ Day 22 ได้ตรง

วิธี พื้นที่ประเทศไทย (ตร.กม.)
SQL ST_Area_Spheroid (ป้อนกลับด้าน) 514,453.7
pyproj geodesic (Geod.geometry_area_perimeter) 514,453.7 (ต่าง 0.00)
ค่าที่ซีรีส์ใช้จริง (ระนาบ Equidistant Conic) 512,593.1 = ต่ำกว่า geodesic −0.3617%

บรรทัดสุดท้ายคือตัวเลขที่ผมวัดไว้ใน Day 22 (คลาดพื้นที่ของ projection ที่ซีรีส์ใช้) และวันนี้เครื่องมือใหม่คำนวณอิสระแล้วได้ค่าเดิมเป๊ะ — สำหรับผม นี่คือหลักฐานว่า “ลองเครื่องมือใหม่” ไม่ได้แปลว่า “เปลี่ยนคำตอบ” แต่แปลว่า “มีพยานอีกปาก”

(สำหรับจังหวัดเชียงใหม่ pyproj ให้ 22,759.6 ตร.กม. ส่วน SQL ที่ป้อนลำดับมาตรฐานได้ NaN ตามกับดักข้อ ๑)

๗. แล้วเรื่องความเร็ว?

งานขนาดนี้ (83 จุด × 4,596 polygon, 83 × 163 ห่วง, 83 × 56,946 โหนด) SQL ไม่ได้ชนะแบบน่าตื่นเต้น: A 0.011 วิ vs 0.012 วิ · B 0.002 วิ vs 0.007 วิ · C 0.21 วิ vs 0.31 วิ กรณีเดียวที่ต่างกันชัดคือ “นับจำนวนห่วงประเภท relation” — SQL 0.001 วิ เทียบกับการทำ mask ด้วย numpy ที่ 0.07 วิ (แต่คนละปริมาณงานกัน จึงไม่ใช่การเทียบที่ยุติธรรม) ผมจึงไม่เอาความเร็วมาเป็นเหตุผลในการเปลี่ยนเครื่องมือ — เหตุผลคือ สิ่งที่ได้เรียนรู้ 2 ข้อข้างบน

ว่าด้วยคำศัพท์

  • DuckDB — ฐานข้อมูลแบบฝัง (in-process) ที่ประมวลผลเป็นคอลัมน์ ใช้ SQL กับไฟล์ CSV/Parquet/GeoJSON/shapefile ได้ตรง ๆ โดยไม่ต้อง import เข้า Python
  • duckdb-spatial — ส่วนเสริมที่เพิ่มฟังก์ชัน ST_* (GEOS + PROJ) เข้ามาใน SQL
  • spheroid / ellipsoid — ทรงกลมรีที่ใช้แทนผิวโลก (ที่นี่คือ WGS84) ต่างจาก “planar” ที่วัดบนระนาบพิกัดฉาก
  • geodesic — ระยะ/พื้นที่จริงบนผิว ellipsoid ตามอัลกอริทึมของ Karney ซึ่งทั้งซีรีส์ใช้ ผ่านคลาส Geod ของ pyproj
  • NaN ที่เงียบ (silent NaN) — ค่าที่ผิดแต่ไม่ error ทำให้การคำนวณถัดไปไหลต่อได้จนผิดทั้งสาย
  • Bland–Altman — กราฟพลอต “ผลต่างระหว่างสองวิธีวัด” เทียบกับค่าเฉลี่ย ใช้ตอบว่า เครื่องมือสองตัววัดเหมือนกันไหม แทนที่จะดูแค่สหสัมพันธ์

ข้อจำกัด

  • ผลทั้งหมดเป็นของ build นี้: DuckDB 1.5.5 + spatial eb1e57c บน windows_amd64 — เครื่องอื่น/เวอร์ชันอื่น ST_Transform อาจใช้ได้ ซึ่งจะทำให้กับดักที่ 2 หายไป (สคริปต์มี assert ที่ล้มเมื่อกับดักหายไป เพื่อบังคับให้อัปเดตโพสต์ ไม่ใช่ปล่อยให้อ่านผิด)
  • งาน C วัดระยะไป โหนด ของขอบลำน้ำ ไม่ใช่ตั้งฉากกับตัวเส้น — เป็นนิยามเดียวกับ Day 26 และใช้กล่อง 0.06° เป็น prefilter (สี่เหลี่ยม ไม่ใช่จานกลม) ซึ่งตัดโหนดที่มุมกล่อง ที่ไกลกว่า 5 กม. อยู่แล้วออกไป จึงไม่มีผลกับค่า ต่ำสุด
  • ตารางเทียบชื่อจังหวัดไทย↔︎อังกฤษเกิดจากเสียงข้างมากของ 83 จุด ไม่ใช่ gazetteer จึงมี 5 ชื่อที่กำกวม และตัวเลข “ทะเบียนไม่ตรง NE 5 จุด” ต้องอ่านคู่กับข้อนี้เสมอ
  • ห่วง 163 เส้นเป็นเวอร์ชันลดรายละเอียดของ Day 21 (median 8 จุด/ห่วง) ผล containment จึงต่ำกว่าที่ Day 21 รายงาน 1 จุด — นี่คือข้อค้นพบ ไม่ใช่ข้อผิดพลาด
  • benchmark วัดบนเครื่องเดียว ไฟล์ที่ยังไม่ถูกโหลดเข้าหน่วยความจำครั้งแรกจะช้ากว่ามาก และงานเหล่านี้เล็กเกินกว่าจะวัดความต่างของเครื่องมือได้อย่างยุติธรรม
